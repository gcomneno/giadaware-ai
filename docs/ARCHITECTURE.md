# GiadaWare AI Capability — Architecture

## Status

Approved for M0 architectural proof and hardened by the Semantic Capability
Contract v0.1 for the experimental `0.x` line.

The normative semantic rules are defined in
`docs/SEMANTIC-CAPABILITY-CONTRACT.md`.

## Purpose

Provide GiadaWare products with optional, pluggable AI capabilities while
keeping application authority in deterministic software.

Canonical rule:

> AI processes and proposes; software validates, decides, and executes.

AI output is data, never authority.

## Architectural boundary

A consuming product depends on semantic AI capabilities, not on models,
providers, prompts, or transport details.

Architecture:

    GiadaWare Product
            |
            v
    GiadaWare AI Capability
            |
            v
    AI Backend / Runtime
            |
            v
    Local or remote inference provider

LibreChat is not part of the public contract.

Ollama is an infrastructure implementation detail.

## Normative principles

1. AI is optional.
2. AI has no mutation authority.
3. Consumers depend on semantic capabilities, not prompts or models.
4. AI output is untrusted input.
5. Outputs must be validated before crossing the public library boundary.
6. Backends must be replaceable.
7. Failures must be explicit and typed.
8. Local-first does not mean local-only.
9. The architecture may enable zero-cost local inference, but does not promise
   that every backend is free.
10. Provider and model identity must not leak into product domain semantics.
11. Structural result stability does not imply deterministic inference content.
12. Fallback must not silently change semantic, privacy, locality, or cost
    guarantees.
13. Consumer artifact provenance and workflow authority remain consumer
    responsibilities.

## Semantic capability boundary

A semantic capability expresses reusable consumer intent rather than provider
mechanics. It is provider-independent, read-only, side-effect-free, typed, and
validated before returning data to the consumer.

Provider primitives such as raw prompts, chat/completion calls, or
provider-specific structured-output APIs are backend implementation details and
are not public semantic capabilities.

The complete admission, compatibility, provenance, and trust rules are defined
in `docs/SEMANTIC-CAPABILITY-CONTRACT.md`.

## Capability family layer

Contract v0.1 defines twelve canonical semantic capability families:

- Analyze;
- Summarize;
- Classify;
- Extract;
- Compare;
- Explain;
- Identify;
- Generate;
- Propose;
- Transform;
- Synthesize;
- Detect.

They organize extension semantics; they are not generic inference entry points.
A family may have zero, one, or many concrete capabilities.

The intended hierarchy is:

    SemanticCapability
        |
        v
    Capability Family
        |
        v
    Concrete Capability
        |
        v
    optional Consumer Specialization

For example:

    AnalyzeCapability
        -> AnalyzeLogCapability
        -> AnalyzeLearningSourceCapability
        -> consumer-specific analysis capability

Family membership follows the primary consumer-facing semantic intent, not the
internal steps taken by a model. The existing `analyze_log()` behavior maps to
Analyze without changing its public M0 behavior.

Consumer-specific specializations may remain outside the GiadaWare AI public
catalog while inheriting the global read-only, provider-independent,
side-effect-free, typed, validated, advisory, and explicit-failure contract.

The Python extension surface uses generic abstract base classes for semantic
family membership, a `CapabilityFamily` enum for stable family identity, and
composition with the structural `AIBackend` protocol for provider replacement.
The family ABCs are intentionally thin: semantic inheritance is explicit without
forcing provider plumbing or consumer-specific capabilities into the core
package.

The rationale and extension rules are documented in `docs/EXTENSION-API.md`.

## Mutation boundary

The AI layer MUST NOT directly:

- modify application state;
- persist domain data;
- write or delete consumer files;
- perform Git mutations;
- send messages;
- change permissions or configuration;
- perform transactions;
- invoke destructive operations.

Any effect on application state belongs exclusively to the consuming software.

## Trust boundary

The architecture distinguishes:

    consumer input
          |
          v
    raw inference          <- untrusted
          |
          v
    validation
          |
          v
    typed AI-derived result
          +
    trusted library metadata, when exposed

Validation proves conformance to the semantic result contract. It does not
prove factual truth, approval, correctness, safety, or authority unless a
future capability explicitly and independently defines such a guarantee.

Trusted technical metadata must be generated by GiadaWare AI code, not copied
from model output.

## Backend boundary

A backend adapts inference transport and provider behaviour. It does not define
application semantics.

Backends may handle provider invocation, authentication, timeouts, structured
output, safe retry policy, and typed error translation.

Backends must not mutate consumer state, bypass result validation, leak
provider-specific objects into semantic result types, or redefine capability
meaning.

## M0 capability

The first supported semantic capability is:

    analysis = ai.analyze_log(log_text)

The consumer receives a validated typed `LogAnalysis`, not raw model output.

## Failure model

All public AI failures derive from `AIError`.

The shared M0 exception surface includes:

- `AIConfigurationError`;
- `AIUnavailableError`;
- `AITimeoutError`;
- `AIInvalidResponseError`;
- `AIUnsupportedCapabilityError`.

`AITimeoutError` is semantically an availability-related failure, but the M0
Python API currently exposes it as a sibling of `AIUnavailableError`. Any future
exception-hierarchy change during `0.x` must be intentional and documented.

Failures must not be converted silently into empty or success-looking results.

Failure of an optional AI capability must degrade that feature rather than the
deterministic base product, unless the consumer explicitly declares the
capability required.

## Fallback model

Fallback is a composition-layer decision.

A local backend failure MUST NOT silently redirect private input to a remote
provider. Any fallback that changes locality, privacy, semantic, or cost
guarantees must be explicitly configured by the consuming application or its
deployment composition.

## Compatibility boundary

Public compatibility covers capability names, documented inputs, result types,
field semantics, enumerations, exception hierarchy, and behavioural guarantees.

Prompts, models, provider envelopes, transports, sampling parameters, and retry
implementation are not public contract unless deliberately promoted.

During `0.x`, breaking changes may occur but must be intentional and
documented. The detailed rules are defined by the Semantic Capability Contract.

## Provenance boundary

GiadaWare AI may expose trusted technical invocation metadata separately from
semantic result data.

Consumer artifact concerns remain outside the library semantic result contract,
including filesystem paths, input hashes, persistence envelopes, pipeline
association, restart/reuse semantics, approval state, and labels such as
`ai-advisory`.

## M0 acceptance criteria

M0 proves:

- public semantic capability contract;
- typed and validated results;
- replaceable backend protocol;
- Ollama-backed implementation;
- fake-backend contract tests;
- real local integration test;
- graceful unavailable-AI behaviour;
- absence of mutation primitives.

Contract hardening extends those guarantees without changing the fundamental M0
boundary.

Chat, agents, MCP, RAG, memory and LibreChat integration are explicitly outside
M0 scope.
