# AGENTS.md

Operational contract for coding agents working anywhere in this repository.

GiadaWare AI is an experimental `0.x` infrastructure library for optional,
pluggable, read-only AI capabilities. Its central rule is:

> AI processes and proposes; software validates, decides, and executes.

AI output is data, never authority.

## Canonical Documents

Read the relevant source-of-truth documents before touching a boundary:

- Start with `README.md` and `docs/ARCHITECTURE.md` for the repository purpose,
  public posture, architectural boundary, mutation boundary, trust boundary,
  failure model, fallback model, and provider/runtime posture.
- Use `docs/SEMANTIC-CAPABILITY-CONTRACT.md` for normative rules about public
  semantic capabilities, result contracts, extension admission, compatibility,
  authority exclusions, and failure semantics.
- Use `docs/BACKEND-CONTRACT.md` before changing `AIBackend`, backend adapters,
  structured-output behavior, schema-constrained generation, or backend error
  mapping.
- Use `docs/PROVIDERS.md` before changing provider docs, provider status,
  credential guidance, runtime-verification language, or backend availability
  claims.
- Use `docs/QUALIFICATION-ADMISSION.md` before changing qualification,
  admission, reviewed evidence, capability/composition identity, or evaluation
  semantics.
- Use `docs/TRANSLATION-CONTRACT.md` before changing translation request/result
  semantics, localization boundaries, or translation validation.
- Use `docs/SEMANTIC-READ-QUERY.md` before changing semantic read-query
  interpretation, context loading, grounding, candidate-query validation,
  qualification, or execution-authority language.
- Use `docs/EXTENSION-API.md` before changing semantic capability family
  classes, `CapabilityFamily`, `SemanticCapability`, or consumer extension
  rules.
- Use `docs/COMMANDS-LAYER.md` only for the custom conversational command
  aliases and their repository-routing implications.
- Use capability-specific files under `docs/qualification/`, `docs/research/`,
  and `experiments/*/README.md` only for their scoped evidence or experiment.

Do not duplicate these documents into code, tests, or this file. Prefer a short
reference to the canonical document when a detailed contract already exists.

## Architectural Invariants

- AI is optional, advisory, read-only, and side-effect-free.
- Providers, models, prompts, endpoints, SDKs, and transport envelopes are
  implementation details unless a canonical document deliberately promotes
  them.
- Consumers depend on semantic capabilities and typed, validated results, not
  raw prompts, raw model output, provider objects, or model-specific behavior.
- Raw inference is untrusted input. Validation is required before data crosses
  the public library boundary.
- Validation establishes contract conformance only. It does not establish
  factual truth, business validity, approval, safety, execution authority, or
  semantic qualification unless a future reviewed contract explicitly says so.
- Trusted technical metadata, when exposed, must be generated by GiadaWare AI
  code. A model must never self-assert trusted metadata.
- Failures must remain explicit and typed. Do not convert failures into empty
  values, fabricated defaults, or success-looking results.
- No provider, backend, or semantic capability may mutate consumer state, write
  or delete consumer files, perform Git mutations, send messages, change
  permissions/configuration, execute tools, perform transactions, authorize
  queries, or publish content.
- Fallback that changes semantic, privacy, locality, or cost guarantees must be
  explicit at the composition boundary. Do not add automatic provider routing
  or fallback unless a separate reviewed contract designs and approves it.

## Provider And Backend Boundaries

`AIBackend` is the provider-independent inference boundary. It may expose
provider-independent primitives such as `generate_json()`, but it must not leak
provider request fields, model-specific options, runtime objects, provider SDK
objects, or transport semantics into consumer domain code.

Structured output constrains representation; it does not grant authority. A
backend that cannot satisfy a required schema-constrained primitive must raise
the documented typed failure instead of silently downgrading to unconstrained
generation.

Do not force semantically different providers or decision systems into
`AIBackend` merely for protocol uniformity. A provider belongs behind the
boundary that matches its actual semantics.

Provider account, billing, credential, HTTP availability, timeouts, and
transport failures are operational/backend concerns. They are not semantic
qualification failures.

## Qualification And Admission

Keep these states separate:

- supported backend: an implemented adapter that satisfies the backend
  contract;
- runtime-verified backend: a real provider path observed through the shared
  backend boundary;
- semantically qualified composition: a specific
  `capability x backend/model x operating envelope x evaluation evidence`
  admitted by reviewed qualification evidence.

Backend/model availability does not imply semantic capability qualification.
Runtime verification does not imply semantic capability qualification.
Structured output does not imply semantic competence.

Admission, when implemented for a capability, is deterministic and occurs
before provider inference. Missing, stale, mismatched, failed, or
out-of-envelope evidence must not trigger fallback inference or a silent
downgrade.

Deterministic consumer-owned validation remains authoritative. Consumers retain
all execution, authorization, persistence, publication, and workflow authority.

## Experiments

Treat everything under `experiments/` as experiment-only unless a canonical
document and production code explicitly promote it.

- Experiments do not become supported public capabilities merely by existing,
  passing tests, or producing useful evidence.
- Experiment contracts are scoped to their experiment directory and README.
- Do not move experiment semantics into `src/giadaware_ai`, public docs, or
  public result types without an explicit reviewed promotion path.
- Preserve existing experiments unless the user explicitly scopes work to them.
- Passing deterministic experiment tests is not semantic qualification for a
  real provider/model composition.

## Secrets And Credentials

Credentials and secrets must never enter repository files, tests, logs,
fixtures, captured outputs, examples, docs, or prompts committed as artifacts.

Remote credentials are injected by consumers through environment variables or
an external local secret store. Provider account and billing availability are
operational prerequisites, not repository state and not semantic capability
evidence.

Do not add real tokens, billing details, account identifiers, private
endpoints, or credential-derived output to documentation or tests.

## Workflow

1. Inspect before editing. Read the relevant canonical documents, nearby code,
   tests, and existing error/result contracts.
2. Keep changes narrowly scoped. Do not refactor unrelated areas or alter
   experiments, production code, docs, or fixtures outside the user request.
3. Reuse existing typed errors, result contracts, validators, and boundaries.
   Do not invent parallel semantics when the repository already has a contract.
4. Add or update focused deterministic tests for changed behavior. Unit tests
   should not depend on exact natural-language model output.
5. Run relevant focused tests first, then established repository checks before
   declaring completion.
6. Run `git diff --check`.
7. Report production behavior, public-contract, provider-boundary,
   qualification, secret-handling, or experiment-scope changes explicitly.

## Verification

Use the repository's portable commands from an active Python environment. The
project supports Python `>=3.11`; CI runs Python 3.11 and 3.12.

Expected baseline checks:

```bash
PYTHONPATH=src python -m unittest discover -s tests/unit -v
python -m compileall -q src tests
python -m pip install --upgrade pip build
python -m build
python -m venv /tmp/giadaware-ai-consumer
/tmp/giadaware-ai-consumer/bin/pip install dist/*.whl
cd /tmp
/tmp/giadaware-ai-consumer/bin/python -c "from giadaware_ai import AICapabilities, LogAnalysis, Severity; from giadaware_ai.backends import OllamaBackend; print('installed-wheel import OK')"
git diff --check
```

Run narrower focused tests first when appropriate. Run opt-in integration,
qualification, or experiment commands only when the task requires them, the
needed local runtime or credentials are explicitly available, and the relevant
canonical document describes the command.

Where an experiment README documents `python3`, follow that experiment's
command. Do not encode a host-specific Python executable path here unless a
future durable local workflow document deliberately establishes one.
